# coe-sdd — Spec-Driven Development

Plan and implement projects with governed artifacts. Feature-by-feature, orchestrated milestone-by-milestone. Constitution-checked. Zero hardcoded conventions.

Control repository (this workspace) holds `.specs/`; application code lives in separate code repos under a chosen layout (A/B/C). The IDE rule with layout + Git is **generated by `coe-sdd-init`** from the skill template.

Foundation is layer 0 for **greenfield** only. **Brownfield** maps the codebase first and does not require `.specs/foundation/`.

**Artifact language:** all generated product docs (PROJECT, ROADMAP, CONSTITUTION, STATE, codebase/*, feature specs/plans/tasks, IDE rule body) follow the skill templates in **pt-BR**, same policy as `foundation-docs`. Keep IDs (`FR-*`, `US-01`, `T001`, file names) stable.

```
┌──────────┐   ┌──────────┐   ┌──────────────┐
│   INIT   │ → │   PLAN   │ → │  IMPLEMENT   │
└──────────┘   └──────────┘   └──────────────┘
 PROJECT        spec · plan    ensure branch
 ROADMAP        data-model     task-by-task
 CONSTITUTION   contracts      gate + review
 STATE · rule   tasks          + commit
 layout · Git
```

Secondary: `coe-sdd-status` · `coe-sdd-pause` · `coe-sdd-resume`

## Artifact Selection

Before generating artifacts, list what will be created and what will be omitted — with justification. Ask for confirmation before proceeding.

**Core — always present in `coe-sdd-plan`:**
`spec.md` · `plan.md` · `tasks.md` · `checklists/requirements.md`

Every product User Story in `spec.md` gets a Fibonacci story point (source of truth, echoed in `plan.md` and `tasks.md`) — see [story-points.md](references/story-points.md).

**Conditional — generated only when the work requires it:**

| Artifact | Generate when |
|----------|---------------|
| `research.md` | Relevant technical decision or `[NEEDS CLARIFICATION]` in spec |
| `data-model.md` | New or changed entities / tables / schema |
| `contracts/` | Exposed interface: internal or public API, CLI, events, UI contracts |
| `quickstart.md` | Non-trivial E2E or manual validation needed |
| `context.md` | Architectural/UX discuss explicitly triggered |

## Milestone vs Feature

The planning unit is determined by the **ROADMAP structure**, not by the milestone number.

| ROADMAP structure | Planning unit | Output folder |
|-------------------|---------------|---------------|
| Milestone **with** `### Features` | One per feature entry | `.specs/features/{MN}-{feature-slug}/` |
| Milestone **without** `### Features` (scope-only) | The milestone itself | `.specs/features/{MN}-{milestone-slug}/` |

**Rules:**
- Each `coe-sdd-plan` invocation produces **exactly one folder**.
- The `{MN}-` prefix is mandatory on every folder (e.g. `M1-authentication-session`, `M0-bootstrap`).
- Never consolidate multiple entries under `### Features` into a single folder.
- After each `coe-sdd-plan`: mark the feature `PLANNED` in ROADMAP.md and link to its folder (e.g. `PLAN ✅ → .specs/features/M1-authentication-session/`). For scope-only milestones, mark the milestone block directly.

## Workflow

**Greenfield:**
1. `coe-sdd-init` — requires foundation → PROJECT + ROADMAP + CONSTITUTION + STATE + `_templates/` → user picks layout A|B|C → confirms Git pattern → generates IDE rule from skill template
2. `coe-sdd-plan M0` — scope-only milestone → single folder `M0-bootstrap/` (no git branch)
3. `coe-sdd-implement M0-bootstrap` — ensure feature branch in the target **code** repo (refuse `main`/`prod`/…), then tasks; for milestones with Features: one `coe-sdd-plan` + `coe-sdd-implement` per feature

**Brownfield:**
1. Detect brownfield (intent or heuristic: code present, no `.specs/project/PROJECT.md`) → [brownfield.md](references/brownfield.md) first — **no foundation required**
2. `coe-sdd-init` continues from codebase docs (+ optional foundation enrichment only) → layout + Git + IDE rule
3. Plan from M1 (M0 marked `✅ done` if infrastructure already exists)

## Context Loading

| Situation | Load |
|-----------|------|
| `coe-sdd-resume` / session start | PROJECT.md + ROADMAP.md + STATE.md (`<15k tokens`) |
| `coe-sdd-plan MN` | + CONSTITUTION.md + spec/plan/tasks of the current feature (`MN-{feature-slug}`) |
| `coe-sdd-implement MN` | + tasks.md of the current feature folder + TESTING.md + CONVENTIONS.md |
| Brownfield active | + ARCHITECTURE.md + CONCERNS.md (on demand) |

**Never load simultaneously:** multiple feature specs.
**Target:** `<40k tokens`. Alert with 🔴 when exceeded. See [context-limits.md](references/context-limits.md).

## Sub-Agent Delegation

| Activity | Delegate? | Why |
|----------|-----------|-----|
| Brownfield mapping | Yes | Output is large; only summary matters |
| Implementing a task | Yes | File reads/edits consume context |
| Parallel `[P]` tasks | Yes (one per task) | Only way to truly parallelize |
| Sequential tasks | Yes | Keeps implementation artifacts out of main context |
| Planning / task creation | No | Requires full accumulated context |

Each sub-agent receives: task definition (What/Where/Depends/Tests/Gate) + CONVENTIONS.md + TESTING.md + relevant spec context.
Returns: Status · Files changed · Gate result · SPEC_DEVIATION markers.

## Knowledge Verification Chain

```
1. Codebase      → existing code, conventions, patterns already in use
2. Project docs  → .specs/foundation/, README, inline comments
3. Context7 MCP  → library APIs, current patterns
4. Web search    → official docs, community patterns
5. Flag uncertain → "I'm not certain — here's my reasoning, but verify"
```

Never skip to Step 5 if Steps 1–4 are available.
Never fabricate APIs, patterns, or behaviors. Uncertainty beats fabrication.
